# Walk — external coding agent drives discovery via `pulse mcp`

**Spine `r2.s1`, RELEASE.md criteria 1–3 / ledger `d14`.**

> This walk proves the spine's end state on a MacBook: an external coding
> agent (Claude Code) drives a discovery loop through `pulse mcp` — export the
> fixture, submit a DSL variant with a hypothesis, backtest it over a date
> window — and the desktop visibly attributes the child run to
> `external_agent · claude-code` beside its parent. It is dispatched as an
> **Orca session in the `macbook` environment** (ruling a14). The stopwatch
> runs from the first MCP tool call to the child run visible in Backtest Lab;
> the budget is **10 minutes**.

## Setup (preconditions — done before the timer starts)

1. **Seeded fixture.** The Release 1 fixture is in place: BTCUSDT **M15 + H4**
   CandleSeries snapshots at a pinned `data_version`, and a migrated
   `pulse.db` at `~/Library/Application Support/PulseTrader/pulse.db`. Record
   the pinned `data_version` — the exports below must carry it.
2. **Bundle built.** `just bundle` has produced
   `/Applications/PulseTrader.app` (or the walker's local equivalent) at the
   current head. The MCP server is the bundle binary's `mcp` subcommand — the
   app and the server are one build, so there is no version skew.
3. **Client configured.** Claude Code is registered against the bundle binary
   per `docs/mcp-client.md`:
   `claude mcp add pulse -- /Applications/PulseTrader.app/Contents/MacOS/pulse mcp --agent-name claude-code`.
   No `--db`, no `--data-dir` — the server shares the app's data dir.
4. **App running.** `PulseTrader.app` was launched from Finder and is sitting
   on the Strategy Library. (WKWebView delivers `focus` on activation — the
   C2 refetch this walk proves needs a real app switch, not a backgrounded
   window.)
5. **Agent session open.** A Claude Code session with the `pulse` server
   connected — `claude mcp list` shows `pulse` as connected. The agent holds
   no prior context about the fixture; everything below is driven through
   tool calls.

## The walk (stopwatch starts at the first tool call)

**Step 1 — Export the fixture (budget: ~2:00)**
- Agent calls `export_candles` twice —
  `{ "pair": "BTCUSDT", "timeframe": "15m", "data_version": "<pinned>" }` and
  `{ "pair": "BTCUSDT", "timeframe": "4h", "data_version": "<pinned>" }` —
  then `export_indicators` with
  `{ "pair": "BTCUSDT", "timeframe": "15m", "data_version": "<pinned>", "indicators": ["rsi:14", "adx:14"] }`.
- *Expected output:* three absolute paths under
  `~/Library/Application Support/PulseTrader/exports/<pid>-<start-unix-ms>/`,
  each reply carrying the pinned `data_version`, a row count, and
  `timeframe`/`pair` echoing the request. The files are operator-owned and
  stay after the session ends.

**Step 2 — Read the parent, then submit a structural variant (budget: ~2:30)**
- Agent calls `list_strategies` (`{ "include_archived": false }`), picks the
  walk's parent version — a root version created earlier in this same walk,
  either through the Designer's compose flow or by an earlier
  `submit_strategy_version` root call (`strategy_name` form) — then calls
  `submit_strategy_version` with a real structural change and a stated
  hypothesis:
  ```json
  {
    "parent_version_id": "<parent version id>",
    "dsl": { "…the variant document…" },
    "hypothesis": "ADX > 20 filter suppresses entries when there is no trend, lifting expectancy."
  }
  ```
  Exactly one of `parent_version_id` / `strategy_name` is passed; `dsl` is the
  submitted document; `hypothesis` is required.
- *Expected output:* `{ "version_id": "<new id>", "strategy_id": …,
  "created_by": "external_agent", "agent_name": "claude-code", … }` — the
  child version's id, attributed to the flag-resolved agent name.

**Step 3 — Prove the validation path (budget: ~1:00)**
- Agent calls `submit_strategy_version` again with a deliberately invalid
  document (e.g. an `entry` the grammar rejects, or a missing required field).
- *Expected output:* a tool error shaped `{ "field", "message" }` naming the
  offending DSL path — correctable, nothing persisted. A second
  `list_strategies` shows **no new version** under the parent.

**Step 4 — Backtest the child over a date window (budget: ~1:30)**
- Agent calls `run_backtest` with an explicit RFC 3339 UTC window:
  `{ "version_id": "<child version id>", "from": "2025-03-01T00:00:00Z", "to": "2025-06-01T00:00:00Z" }`
  (`from`/`to` are both-or-neither; omitting both falls back to the parent's
  inputs).
- *Expected output:* `{ "run_id": "<run id>", "version_id": "<child id>",
  "run": { … } }` where `run.inputs.window` echoes `{from_ms, to_ms}` of the
  requested window — the run is recorded against the child with the window in
  its persisted inputs.

**Step 5 — Bring the app forward (budget: ~0:30)**
- Switch to the already-running `PulseTrader.app` — a real app activation
  (Cmd-Tab or the Dock), not a new launch. Stay on the Strategy Library; do
  not navigate.
- *Expected output:* within a beat of focus, the Library refetches and the
  new child version appears **under its parent**, labelled
  `external_agent · claude-code` with the hypothesis as a subline — no
  refresh gesture, no navigation. Selecting it shows the full hypothesis in
  the details pane.

**Step 6 — Compare child against parent (budget: ~1:30)**
- Open Backtest Lab and select the child version in the catalog.
- *Expected output:* a **Compare with parent** section renders the child's
  run beside the parent's latest run — columns `before (parent)` /
  `after (child)` — with an `inputs differ` badge when the persisted inputs
  are unequal (the explicit `from`/`to` window makes them so whenever the
  parent's run used a different or default window; hovering the badge shows
  the reason).

**Stopwatch stops** when the child's run is visible in Backtest Lab (end of
Step 6). Target: **≤ 10:00** from the Step 1 `export_candles` call.

## Report back

The walk report records:

- elapsed wall-clock (first tool call → child run visible in Backtest Lab);
- the child `version_id` and `run_id`;
- the pinned `data_version` the exports carried;
- a screenshot of the Library node showing `external_agent · claude-code`
  and its hypothesis subline;
- a screenshot of the Backtest Lab compare (badge visible if inputs differed);
- any step whose actual output diverged from *Expected output*.

## Recovery (if something breaks mid-walk)

- **Tool list is short a tool:** the client is pointed at a stale binary —
  re-check precondition 2/3 (`claude mcp list`, then `claude mcp add` again
  against the current bundle). The write tools live in the same binary as the
  reads; there is no second server to start.
- **`submit_strategy_version` keeps failing on field errors:** that *is* the
  Step 3 evidence — capture one `{ "field", "message" }` and move on with a
  corrected document. Do not keep retrying past the budget.
- **`run_backtest` reports no HEAD snapshot:** the fixture's `data_version`
  was not pinned, or the server's data dir is not the app's — the classic
  symptom of a stray `--data-dir`. Re-check the client config against
  `docs/mcp-client.md`.
- **The child does not appear on focus (Step 5):** confirm the app was
  *activated*, not merely un-minimized from a full-screen Space — WKWebView
  delivers `focus` on activation. Click the Library once; if the child still
  does not appear, the failure is real — capture the state and report it,
  don't paper over it.
- **Compare shows no badge (Step 6):** expected when the parent's latest run
  already used the same window — `inputs differ` only appears when the
  persisted `BacktestInputs` are provably unequal. The compare itself is the
  criterion; the badge is evidence of the window taking effect.
- **Over budget at Step 4:** the backtest is the slow step; the rest is I/O.
  If the run is still going at ~6:00 elapsed, keep the stopwatch running —
  the report records the real elapsed time, not a trimmed one.
